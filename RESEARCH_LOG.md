## Phase 2: the fp64 certificate was fake — fp32 Wigner-3j in every checkpoint — 2026-08-04

**Hypothesis.** Run the deferred `src/ntu_paired_camera.py` (R1 Haar-SO(3) rotation control + P1
real paired-camera consistency) and report it. The theorem predicts R1 ~ 0 for the EGRU.

**What actually happened: the run failed its own precision gate twice, for two different reasons.**

### Defect 1 — `--dtype float64` never reached the input path

`ntu_dataset.preprocess` hard-pinned `np.float32` at entry (`_fit_bodies(np.asarray(kp,
dtype=np.float32))`) and at `out = np.zeros(..., dtype=np.float32)`. `score()` upcast with
`.astype(np_dt)` AFTER the fact, so the fp64 run was an fp32 input path bolted to an fp64 network.
The root subtraction — where the rounding that limits measurable drift happens — was always fp32.

Measured: fp32 4.482e-04 -> fp64 4.003e-05, a drop of only **11x**. CLAUDE.md Task 6 wants r >= 1e5.

Fixed by threading `dtype=np.float32` (unchanged default, so every training/eval caller is
byte-identical) through `preprocess` and `view_normalize`, and passing it INTO preprocess rather than
onto its result. `liveness_mask` takes the same dtype, because its body-selection argsort ranks
bodies by a motion norm and a different precision can order a near-tie differently.

After the fix: fp64 1.265e-07. Better by 3543x — and still failing.

### Defect 2 — the checkpoint re-poisons the model AFTER the dtype guard

Bisected the residual by stage:

| stage | fp64 error | verdict |
|---|---|---|
| preprocess equivariance `P(Rx)` vs `R.P(x)` | 9.44e-16 | exact |
| encoder scalars (must be invariant) | 6.11e-09 | **broken** |
| invariant cut | 5.73e-08 | inherits |
| logits | 2.84e-08 | inherits |

Ruled out, each by measurement rather than argument:
* **the `1e-6` epsilon in `vhat = v/(norms+1e-6)`** — sweeping it 1e-6 -> 1e-12 -> 1e-30 leaves the
  result bit-identical at 5.734e-08. (At exactly 0 it is NaN, which is why it exists: 200/20000
  channels have `||v||` exactly 0.)
* **GPU kernels / TF32 / atomics** — CPU and CUDA agree to every digit (2.837e-08) and the forward is
  bitwise deterministic.
* **zero-padded frames** — they contribute exactly 0.000e+00; the error is in VALID frames.
* **near-degenerate bones** — the 1/||r|| amplification law is real and was confirmed (||r||=1e-8 ->
  4.3e-9, ||r||=1e-10 -> 4.5e-7), but real NTU clips have min||r|| ~ 1e-2, and `||r||` exactly 0 is
  safe (3.68e-16, e3nn guards it). It is *near*-zero that is poison, and real data has none.
* **catastrophic cancellation from trained weights** — trained intermediates peak at 8.06, predicting
  a 1.8e-15 floor against 6.1e-09 measured. Falsified by 7 orders.

**The cause.** e3nn registers the Wigner-3j coupling tensors as PERSISTENT buffers inside the
compiled tensor product (`tps.N._compiled_main_left_right._w3j_1_2_1`), so they are written into
every checkpoint saved from an fp32 run. `load_arm` correctly set the default dtype before
construction — the trap this repo already knew about — and then `load_state_dict` overwrote the
correctly-built fp64 constants with the fp32-rounded copies. The guard was doing its job and the
load undid it.

Causality, not inference:

| encoder | scalar equivariance error |
|---|---|
| fresh fp64, random weights | 3.608e-16 |
| fresh fp64 + checkpoint `state_dict` | **6.106e-09** |
| `load_arm()` as the probe built it | 6.106e-09 |
| `load_arm()` after dropping `_w3j` keys | **1.221e-14** |

fp32 eps (1.2e-7) x output scale ~5 lands exactly on the observed 6e-9. Loading these is never right
at any dtype: they are structural constants fixed by the irreps, so a freshly built tensor is exact
by construction while the checkpoint's copy carries whatever precision the training run happened to
use. The fix drops `_w3j` keys and asserts they are the ONLY missing ones, so a genuinely absent
weight still fails loudly.

**Gate, after both fixes:**

| arm | fp32 | fp64 | ratio |
|---|---|---|---|
| EGRU (ours) | 4.482e-04 | **8.504e-14** | **5.3e9** |
| ST-GCN | 7.256e+00 | 7.249e+00 | 1.001 |

Task 6 wants r >= 1e5; ours clears it by four orders. The control is the other half of the result:
ST-GCN's 7.25 does not move with precision, so its viewpoint error is structural, not numerical.
Ours collapses to machine precision, so the drift IS roundoff and the invariance is exact.

**Blast radius — not yet closed.** 132 checkpoints under `outputs/` carry fp32 `_w3j` buffers
(every e3nn checkpoint in the project). Only `ntu_paired_camera.load_arm` is fixed. The one that
matters for a published number is `src/precision_budget.py` (F7c): it measures the same quantity
(`inv_floor = max_g ||inv(g.x)-inv(x)||/||inv(x)||`) and loads `outputs/cde_block2/egru_pooled_f0.pt`,
which has 2 fp32 `_w3j` keys, via the same construct-then-load pattern. Its fp64 row is the paper's
"exactness anchor". **It must be re-run before that number is trusted** — its own docstring warns
about the construction-time half of this trap while the load-time half went unguarded.
`run_xview_evaluation.py` (the X-View certificate path) has the same pattern.

### Defect 3 — the first full run returned NaN, and a dead guard was why

The first all-triples run exited 0 and reported `max|dlogit| nan` for the EGRU. It also reported
`agreement 100.00%`, which was NOT trustworthy: agreement is an argmax comparison, and two all-NaN
rows both argmax to 0 and score as agreeing. A green headline sitting on top of a NaN.

152 / 18,674 clips (0.814%) produced non-finite logits. Predicted signature matched 1:1 with no
false positives or negatives: **152 clips contain a fully-dead frame on a present body**, and the
intersection with the NaN set is exactly 152. Cause is a second person entering partway through a
clip — `preprocess` marks the body present because it has content somewhere, while the frames before
arrival are entirely untracked.

In `InvariantProjection.forward` the masked amax substitutes `torch.finfo(pj.dtype).min` for dead
joints. When NO joint is live the whole row stays at that sentinel and overflows the head to +-inf,
then to NaN. The guard meant to catch this was already there and had never once fired:

```python
amax = torch.nan_to_num(amax, neginf=0.0)     # all-dead -> 0, not -inf
```

`finfo.min` is **-3.4e38, a finite number**, not `-inf`, so `nan_to_num` passes it through untouched.
The intent was right and the sentinel and the guard simply did not match. Fixed with an explicit
`torch.where(mj.sum(1) > 0, amax, 0)`, which is what the mean branch already does via
`cnt.clamp(min=1)`. It is a no-op whenever any joint is live, so clean clips are bit-identical.
After: 0 / 18,674 non-finite.

This path is new to this probe — training gates a k~U[0,4] joint freeze (never a whole frame) and the
X-View eval path passed `mask=None` — so no trained weight or published number is retro-contaminated.

### Results (all three defects fixed; 18,674 triples fp32, 500-triple fp64 certificate)

**R1 — Haar-SO(3) rotation control on C001. This is the clean result.** R1 is a WITHIN-MODEL
self-comparison (same model, same clip, rotated), so it is immune to every training confound that
killed the head-to-head in the previous entry.

| | agreement | top-1 under rotation | max\|dlogit\| (18,674) |
|---|---|---|---|
| EGRU (ours) | **100.00%** | 82.95 -> **82.95** (0.00) | 4.926e-01 |
| ST-GCN | 91.89% | 80.46 -> 77.44 (**-3.02**) | 1.848e+01 |

Not one prediction in 18,674 changed under a Haar-random rotation. ST-GCN changed 8.11% of them and
lost 3.02 accuracy points.

**Precision-scaling certificate, matched on the SAME 500 triples** (the earlier 5.3e9 was quoted off
an n=24 smoke test and is superseded):

| | fp32 | fp64 | ratio |
|---|---|---|---|
| EGRU (ours) | 1.326e-03 | **2.309e-13** | **5.7e9** |
| ST-GCN | 1.328e+01 | 1.327e+01 | 1.0008 |

Ours collapses to machine precision -> the drift IS roundoff -> the invariance is exact. ST-GCN's
~13 does not move with precision -> its viewpoint error is structural. Task 6 wants r >= 1e5.

**Report the fp32 max honestly: it has a heavy tail.** Over 500 clips the fp32 max is 1.3e-03; over
18,674 it is 4.9e-01, because a max over more clips finds worse-conditioned geometry (the 1/||r||
amplification law characterised above). The fp64 certificate, not the fp32 max, is what establishes
exactness — and note that even in fp32, with a worst-case logit swing of 0.49, agreement stayed
100.00% and top-1 was unchanged.

**P1 — paired camera, 18,674 real simultaneous triples. We do not win this.**

| pair | EGRU (ours) | ST-GCN | role |
|---|---|---|---|
| C1-C2 | 80.23% | **81.31%** | test-vs-train |
| C1-C3 | 78.61% | **79.87%** | test-vs-train |
| C2-C3 | **83.17%** | 82.99% | train-vs-train |
| all three | 73.03% | **73.86%** | |

EGRU is more accurate on every individual camera (82.95/90.20/88.45 vs 80.46/87.08/85.95) and
slightly LESS consistent across a physical camera move. Two caveats, both binding:

1. **The per-camera top-1 columns are the same confounded pair the previous entry CUT** (different

2. **The P1 cross-model comparison inherits those confounds too.** Agreement is scale-free, which
   makes it comparable across logit scales, not across training protocols. The defensible statement

**What R1 and P1 together actually say.** The theorem removes the geometric component of a viewpoint
change exactly (R1: 100.00%, 2.3e-13 in fp64). It removes essentially none of the REST of a real
camera relocation (P1: 73.03%), because the three clips are three different skeleton ESTIMATES of
one event — different tracker noise, occlusion and range — and no property of the read-out can undo
that. Reporting R1 alone would overstate the guarantee by a wide margin. The script's docstring
predicted P1 > R1 for us; it did not predict ST-GCN edging us at P1, and PreNormalize3D absorbing

The first pass left the 0.83pp gap untested because the artifact stored only aggregate means, which

one-off.

The arms are scored on identical triples, so they are paired and an unpaired proportion test would be

| | value |
|---|---|
| ours / ST-GCN all-three agreement | 73.03% / 73.86% |
| discordant triples | 5,394 (ours-only 2,620, theirs-only 2,774) |
| **p (exact binomial, two-sided)** | **0.0372** |

**So it is significant, and I had pre-committed to saying so plainly if it came out this way.**
ST-GCN is genuinely better on P1. The effect is small (0.83pp) but resolvable at $n{=}18{,}674$. The

**`src/precision_budget.py` (F7c) — published number STANDS, script was silently broken.** Measured
the KIMORE checkpoint (`outputs/cde_block2/egru_pooled_f0.pt`, which does carry 2 fp32 `_w3j` keys)
both ways, on F7c's own `inv_floor` metric:

| load | inv_floor (fp64) |
|---|---|
| WITH the checkpoint's fp32 `_w3j` (what the script does today) | 3.788e-10 |
| dropping `_w3j`, fresh fp64 tables | **2.130e-16** |
| **recorded / published fp64 anchor** | **5.750e-16** |

The published 5.750e-16 matches the CLEAN case, so the original run was not poisoned and the number
in the paper is correct. What changed is the environment: re-running the script today would have
quietly produced a 3.8e-10 anchor and called it the theorem. That is a regression that had not yet
reached a paper, caught before it did. Note also the poison (3.8e-10) sits far below the fp32 floor
(2.7e-07), so **only the fp64 row was ever exposed** — the fp16/bf16/int8 curve, which is the actual
precision-budget result, is unaffected either way. `build_at` now drops `_w3j` and keeps every other
key accountable.

Re-ran the patched script end to end. It reproduces the published table:

| precision | recorded (July) | patched re-run |
|---|---|---|
| fp64 | 5.750470791705236e-16 | 5.914715780579368e-16 |
| fp32 | 2.681624850177606e-07 | **bit-identical** |
| fp16 | 0.0026225465181528218 | **bit-identical** |
| bf16 | 0.008341095550913075 | **bit-identical** |

Three rows bit-identical is strong evidence nothing else in the environment moved; the fp64 row
differs by ~3%, which is meaningless for a quantity pinned at the roundoff floor and whose exact
value depends on reduction order. The fp64 verdict still reads EXACT. Decisively: a poisoned July
run would have recorded 3.8e-10, not 5.75e-16 — so the original was clean. `f7c_precision_budget.json`
was rewritten by the re-run; no paper number changes.

What the fix actually buys is independence from a VERSION-DEPENDENT behaviour: whether e3nn persists
`_w3j` into the state_dict, and whether `load_state_dict` then applies it, varies across e3nn builds,
and the certificate silently follows. Dropping the key pins the clean path in every environment.

**`src/run_xview_evaluation.py` — NOT affected. My earlier flag was too broad.** It does contain the
load pattern, but the two things that matter both escape it: `occlusion_test` (the G4 dead-node
self-test, source of `G4 = 0.000e+00`) builds with random weights under an fp64 default and never
loads a checkpoint at all; and `run_sweep`, which does load checkpoints, runs fp32 accuracy only,
where a 1e-10 perturbation is invisible. No reported number there is at risk.

**Standing rule this suggests.** Any fp64 equivariance certificate that loads a checkpoint must drop
`_w3j` (or assert the loaded tables match a freshly built fp64 one). Building under the right default
dtype is necessary and NOT sufficient — the load undoes it, and the failure is silent, plausible-looking
(1e-10 still reads as 'exact' to a skim) and lands squarely on the number the theorem is judged by.
